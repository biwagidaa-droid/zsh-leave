# راهنمای منابع انسانی (HR)

RoleAssignment باید فعال و منقضی‌نشده باشد. سیاست چندنقشی مصوب، scopeهای HR و Manager را در چارچوب شرکت به‌صورت union اعمال می‌کند؛ رکورد محرمانه همچنان فقط در HR assignment مجاز دیده می‌شود. نقش HR به‌تنهایی دسترسی سراسری نمی‌دهد. مرجع و ماتریس API: [سیاست مجوزدهی](../authorization-policy.md).

## کارکنان و سازمان

- «کارکنان» فهرست جست‌وجو و فرم ایجاد/ویرایش پروفایل دارد. فیلدهای ثبت: نام نمایشی، کد پرسنلی، شرکت و داده‌های واحد/مدیر/تاریخ شروع/پایان در request model. HR فقط در scope مجاز می‌تواند مدیریت کند.
- ایجاد کارمند در server نام کاربری `emp-{companyId}-{personnelCode}` و گذرواژه unusable می‌سازد. صفحه ایجاد حساب، صدور گذرواژه، invitation یا reset password در UI موجود نیست؛ پیش از ورود واقعی، رویه هویت‌سنجی/credential باید جداگانه تعریف شود.
- «ساختار سازمانی» در UI شرکت و Department را مدیریت می‌کند؛ مدیریت `OrganizationSite` یا تخصیص نقش در UI پیدا نشد. API شرکت فقط admin را برای تغییر می‌پذیرد؛ کنترل server بر رابط مقدم است.
- «قراردادها» برای کارمند دوره تاریخ، روزهای هفته و درصد قرارداد را ثبت می‌کند. دوره هم‌پوشان رد می‌شود. این اطلاعات با Bradford و روزکاری مصرف می‌شود.

## نوع مرخصی، سهمیه و ورود گروهی

۱. «انواع مرخصی» برای HR/admin انواع فعال را فهرست و تنظیمات `countsAgainstBalance`, `requiresApproval`, `requiresNote`, `requiresReplacement`, `employeeRequestable`, `confidential` و ترتیب را ذخیره می‌کند. قید مدل اجازه نوع confidential و self-requestable را هم‌زمان نمی‌دهد.
۲. «سهمیه‌ها» فهرست `LeaveEntitlement`های سال جاری شمسی را نمایش می‌دهد. فرم اصلاح دستی مثبت/منفی با دلیل در UI وجود دارد. کد API نقش HR یا admin را می‌پذیرد، دامنه HR را روی کارمند اعمال و سرویس دفترکل را برای اصلاح فراخوانی می‌کند؛ آزمون مستقیم endpoint اصلاح در suite موجود یافت نشد و این ممیزی آن را اجرا نکرده است. پیش از استفاده عملیاتی، در DB disposable با fixture مصنوعی اصلاح کنید و نتیجه دفترکل/projection را تطبیق دهید. تغییر مستقیم projection هرگز راه مجاز نیست.
۳. «ورود گروهی» CSV با ستون‌های `personnel_code,type,year,days` می‌گیرد. ابتدا Dry Run اجرا کنید و همه خطاهای ردیف را برطرف کنید؛ ذخیره فقط زمانی انجام می‌شود که هیچ ردیف ردشده نباشد. عملیات در تراکنش است.
۴. سهمیه فقدان یا مغایرت را از روی حدس تکمیل نکنید؛ از «مانده» و پاسخ reconciliation استفاده و دفترکل را با مالک سامانه بررسی کنید. CSV را ابتدا با Dry Run روی fixture جداگانه بررسی کنید؛ commit فقط زمانی انجام می‌شود که هیچ ردیف ردشده‌ای وجود نداشته باشد.

**انتقال و accrual:** مدل/سرویس دفترکل عملیات carry-forward/expiration را پشتیبانی می‌کند و آزمون سرویس دارد؛ اما UI زمان‌بندی، اجرای Job یا ابزار reconciliation عمومی وجود ندارد. accrual دوره‌ای خودکار در UI/Job دیده نشد. انتقال را به‌عنوان عملیات خودکار فعال فرض نکنید.

## درخواست، غیبت و تقویم

- صف «درخواست‌ها» در scope HR را برای نظارت، تصمیم، بررسی و محرمانگی استفاده کنید. HR دامنه‌دار می‌تواند انواع محرمانه را مشاهده/تصمیم کند؛ هر درخواست محرمانه فقط در scope مربوطه.
- «ثبت غیبت» از `POST /hr/absences/` درخواست را مستقیماً در وضعیت تأییدشده ایجاد می‌کند؛ رویداد ثبت و اثر دفترکل در یک تراکنش نوشته می‌شوند و درخواست جداگانه‌ای برای تأیید مجدد وجود ندارد. API به `Idempotency-Key` یکتا نیاز دارد؛ در هر ثبت، تاریخ/نوع/روزکاری/دلیل/کارمند را بازبینی کنید.
- صفحه تعطیلات مدیریت `PublicHoliday` شمسی/غیرفعال‌سازی را نمایش می‌دهد. CRUD جدید تعطیلات نیز در endpointهای `calendar/holidays/manage/` هست، اما صفحه معمول UI از مسیر legacy `/holidays/` استفاده می‌کند؛ تاریخچه از API جدا است.
- `LeavePolicyVersion` و `WorkPattern` نسخه‌دار/دامنه‌دار و در مدل تغییرناپذیرند؛ endpointهای خواندن/ساخت و تاریخچه دارند، اما صفحه کامل مدیریت این موارد در UI معمول یافت نشد. تغییر باید توسط مدیر سامانه و از مسیر مجاز API انجام شود؛ ویرایش رکورد قبلی وجود ندارد.

## گزارش‌ها، Bradford و حسابرسی

- «گزارش‌ها» انواع `absences`, `balances`, `trends`, `process-health`, `bradford` دارد. API گروه کوچک را با `privacy.min_group_size` پنهان می‌کند.
- `bradford` در endpoint عمومی نمودار واقعی برنمی‌گرداند؛ صفحه اختصاصی HR داده‌ی غیبت تأییدشده را بر حسب قرارداد/تقویم تحلیل و یادداشت Bradford را ذخیره می‌کند. یادداشت قابل ویرایش است و AuditEvent معادل آن الزاماً append-only مدل نیست.
- HR در صفحه audit تنها AuditEventهای `LeaveRequest` در scope خود را می‌بیند، نه همه رخدادها.
- Export CSV/XLSX در منطق خالص موجود و آزمون‌شده است، ولی دکمه/API export در UI/API کلاینت دیده نشده است.

## رویه اصلاح امن و خطاها

۱. قبل از اصلاح، شناسه کارمند/شرکت/نوع/سال را با منبع معتبر تطبیق دهید.
۲. برای سهمیه، از adjustment/import استفاده و دلیل روشن وارد کنید؛ event دفترکل را مستقیم تغییر ندهید.
۳. برای تاریخچه/درخواست، رویداد جدید ثبت کنید؛ رکورد append-only را حذف/ویرایش مستقیم نکنید.
۴. پاسخ 404 را نشانه مجاز بودن تلاش مجدد روی ID دیگر تلقی نکنید. 409 reconciliation/تعارض را به مالک سامانه ارجاع دهید.
۵. در تولید داده پزشکی یا Canary واقعی را وارد آزمون دستی نکنید. برای fixture از مقادیر ساختگی استفاده کنید.

تعیین سیاست قانونی سال مرخصی، تخصیص اولیه سهمیه، چرخه accrual، دلیل‌خواهی داخلی و فرایندهای کاربر جدید نیازمند تصمیم/تأیید سازمان است و در کد به‌طور کامل تعیین نشده است. RoleAssignment می‌تواند `expiresAt` آینده (ISO-8601 با منطقه زمانی) داشته باشد؛ تخصیص منقضی/غیرفعال دسترسی نمی‌دهد.
