# راهنمای اعتبارسنجی PostgreSQL

این راهنما برای اجرای واقعی آزمون‌های یکپارچگی روی PostgreSQL است. موفقیت SQLite جایگزین این آزمون‌ها نیست. تست‌رانر Django پایگاه دادهٔ تست تازه می‌سازد و تمام مهاجرت‌ها را روی آن اجرا می‌کند؛ برای تأیید زنجیره از ابتدا، از `--keepdb` استفاده نکنید.

## اجرای محلی با PostgreSQL 17

به Docker و پورت آزاد `55432` نیاز است:

```sh
docker run --rm -d --name zsh-leave-pg-test \
  -e POSTGRES_DB=zsh_pg_validation \
  -e POSTGRES_USER=postgres \
  -e POSTGRES_PASSWORD=pgtest \
  -p 127.0.0.1:55432:5432 \
  postgres:17-alpine

until docker exec zsh-leave-pg-test \
  pg_isready -U postgres -d zsh_pg_validation; do sleep 1; done

cd backend
DJANGO_SETTINGS_MODULE=config.settings_postgres_test \
ZSH_DB_HOST=127.0.0.1 \
ZSH_DB_PORT=55432 \
ZSH_DB_NAME=zsh_pg_validation \
ZSH_TEST_DB_NAME=test_zsh_pg_validation \
ZSH_DB_USER=postgres \
ZSH_DB_PASSWORD=pgtest \
python manage.py test --verbosity 2
```

پس از اتمام، ظرف موقت را متوقف کنید:

```sh
docker stop zsh-leave-pg-test
```

در صورت شکست تست، کد خروجی تست را ثبت و پس از بررسی همان ظرف را متوقف کنید. رمز بالا فقط برای پایگاه دادهٔ محلی و موقت است و نباید در محیط مشترک یا عملیاتی استفاده شود.

## شواهد مورد انتظار

- اجرای آزمون، ساخت پایگاه دادهٔ خالی `test_zsh_pg_validation` و اعمال کل زنجیرهٔ مهاجرت‌های Django را انجام می‌دهد؛ آزمون PostgreSQL نیز وجود مهاجرت نهایی برنامهٔ `leave` را بررسی می‌کند.
- تست‌های PostgreSQL در `leave.tests.test_postgresql`، `leave.tests.test_entitlement_ledger.PostgreSQLEntitlementConcurrencyTests` و آزمون‌های PostgreSQL-only موجود اجرا می‌شوند. در خروجی تست، تعداد آزمون‌های ردشده باید صفر باشد.
- آزمون‌های ledger و تأیید درخواست باید هم‌زمانی رزرو و ثبت تأیید را بدون رکورد تکراری یا ماندهٔ ناسازگار بررسی کنند؛ آزمون‌های append-only باید UPDATE و DELETE مستقیم را با trigger رد کنند.
- آزمون `nulls_distinct=False` باید درج دو تعطیلی سالانه با سال `NULL` و کلید یکسان را رد کند.

## شناسهٔ چندریختی AuditEvent

`AuditEvent.entity_id` از نوع `varchar(64)` باقی می‌ماند: این ستون هم شناسه‌های عددیِ رکوردهای مدل‌های مختلف و هم شناسه‌های متنی مانند `leave-requests` را نگه می‌دارد. تغییر نوع ستون به عددی، داده‌های تاریخی و شناسه‌های غیرعددی را مخدوش یا حذف می‌کند و لازم نیست.

در فیلتر HR، زیرپرس‌وجوهای کلید اصلی با `Cast("pk", output_field=CharField())` به متن تبدیل می‌شوند؛ ستون `entity_id` cast نمی‌شود. آزمون API روی PostgreSQL اجرای همین SQL و بازگشت شناسهٔ عددی به‌صورت رشته را بررسی می‌کند. cast در سمت مقدار زیرپرس‌وجو است، بنابراین نوع و ایندکس احتمالی ستون ذخیره‌شده تغییر نمی‌کند. پیش از هر تغییر در مدل یا مهاجرت مرتبط با این ستون، داده‌های تاریخی و شناسه‌های متنی باید بررسی شوند.

## ارتقای دادهٔ موجود

اجرای تست تازه، زنجیره را از پایگاه دادهٔ خالی می‌آزماید و جایگزین آزمون ارتقای نسخه‌ای از داده‌های واقعی نیست. برای ارتقای عملیاتی:

1. از پایگاه داده نسخهٔ پشتیبان قابل‌بازیابی بگیرید و روی نسخهٔ جداگانه بازیابی کنید.
2. ابتدا همین آزمون‌ها را روی PostgreSQL هم‌نسخهٔ محیط مقصد اجرا کنید.
3. مهاجرت‌ها را روی نسخهٔ بازیابی‌شده اجرا کنید، سپس تعداد رکوردهای `AuditEvent`، شناسه‌های غیرعددی و تریگرهای append-only را بررسی کنید.
4. تا تأیید تطبیق داده‌ها و reconciliation دفترکل، نسخهٔ پشتیبان را نگه دارید.

هیچ مهاجرتی برای تبدیل `entity_id` اضافه نشده است؛ بنابراین برای اصلاح مقایسهٔ زیرپرس‌وجو، بازنویسی یا پاک‌سازی داده‌های تاریخی لازم نیست.

## محدودیت CI

در مخزن در حال حاضر پیکربندی CI وجود ندارد؛ بنابراین workflow جدیدی اضافه نشده است. هنگام افزودن CI، سرویس PostgreSQL 17 را به‌عنوان service راه‌اندازی و همین تنظیمات و دستور تست را به کار ببرید.
