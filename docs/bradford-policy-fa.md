# سیاست و API موقت Bradford

## وضعیت

فرمول خالص موجود در `backend/zsh_core/reports.py` صریحاً `B = S² × D` را با روزهای تقویمی پیاده می‌کند. مستندات تصمیم سازمانی، فعال‌سازی Bradford را منوط به تصویب سیاست کرده‌اند. بنابراین API فقط پس از ثبت تنظیم `bradford.enabled=true` و نوع‌های مشمول اجرا می‌شود و نتیجه را با وضعیت `provisional` برمی‌گرداند؛ این پیاده‌سازی **تصویب یا تکمیل سیاست سازمانی نیست**. پیش‌فرض فعال‌سازی اکنون خاموش است.

## رفتار فعلی سرویس

- **دوره گزارش:** پارامترهای `from` و `to` با قالب ISO (`YYYY-MM-DD`)، هر دو الزامی یا هر دو حذف‌شده. حالت پیش‌فرض ۳۶۵ روز منتهی به تاریخ محلی سازمان است. بازه سفارشی حداکثر ۳۶۶ روز و پایان آن حداکثر امروز محلی است. مرزهای بازه شامل می‌شوند.
- **روز غیبت D:** روز تقویمیِ یکتا در محدوده اشتغال و دوره گزارش. هر تاریخ در بازه درخواست یک روز محسوب می‌شود؛ `working_days` برای شمارش D استفاده نمی‌شود.
- **دوره غیبت S:** بازه‌های هم‌پوشان یا متصل به هم (تاریخ بعدی) در سطح هر کارمند و میان نوع‌های مشمول، یک دوره‌اند. بازه درخواست به دوره گزارش و تاریخ شروع/پایان اشتغال کارمند بریده می‌شود.
- **تعطیلات و تعطیلی هفتگی:** چون روزها تقویمی‌اند، آخرهفته یا تعطیلی رسمی/سازمانی دوره را نمی‌شکند و از D کم نمی‌شود. WorkPattern و درصد قرارداد در این نسخه بر نتیجه اثر ندارند.
- **وضعیت درخواست:** فقط `APPROVED` و `WITHDRAWAL_PENDING` شمرده می‌شوند. درخواست‌های `PENDING`، `ESCALATED`، `REJECTED` و `CANCELLED` شمرده نمی‌شوند. مرخصی تا زمان تأیید لغو، همچنان غیبت تأییدشده تلقی می‌شود.
- **نوع‌های مشمول:** از تنظیم صریح و جداشده با کاما `bradford.include_types` می‌آیند؛ فقط نوع‌های غیرمحرمانه در محاسبه شرکت می‌کنند. نوع محرمانه قبل از هر تجمیع حذف می‌شود و نام، تعداد یا وجود آن در پاسخ بازتاب نمی‌یابد.
- **مرخصی جزئی/ساعتی:** داده فعلی روز/ساعت جزئی را به تاریخ مشخص پیوند نمی‌دهد. اگر `working_days` درخواست مشمول کسری باشد، کل گزارش با `409 incomplete_partial_day_data` متوقف می‌شود؛ امتیاز ناقص یا گرد‌شده برگردانده نمی‌شود. محاسبه ساعتی با `bradford.include_hourly=true` نیز صریحاً رد می‌شود.
- **استخدام:** فقط کارکنانی در جمعیت گزارش‌اند که بازه اشتغال‌شان با بازه گزارش تلاقی دارد. هر غیبت به `start_date` و `end_date` کارمند (شامل هر دو) محدود می‌شود.
- **حریم خصوصی و صفحه‌بندی:** فقط HR با دامنه انتسابی مجاز است؛ داده درخواست‌ها از همان scope محدود می‌شود. صفحه کارکنان انتخاب می‌شود، سپس همه رکوردهای واجد شرایط همان کارکنان خوانده و کامل محاسبه می‌شوند؛ صفحه‌بندی هرگز رکوردهای ورودی یک امتیاز را محدود نمی‌کند. حافظه محاسبه به صفحه محدود است. `limit` پیش‌فرض ۱۰۰ و حداکثر ۲۰۰، و `offset` نامنفی است. اگر اندازه جمعیت از `privacy.min_group_size` کمتر باشد، خروجی سرکوب و `emptyStateReason=minimum_group_size` برگردانده می‌شود.

## قرارداد API

`GET /api/v1/reports/bradford?from=<YYYY-MM-DD>&to=<YYYY-MM-DD>&limit=100&offset=0`

پاسخ موفق شامل `reportingPeriod`، `policy`، `authorizedScope`، `status`، `series` و اطلاعات صفحه‌بندی است. هر سطر `series` شامل شناسه کارمند، کد پرسنلی، نام نمایشی، تعداد دوره‌ها، روزها و امتیاز است؛ این جزئیات فقط برای HR در scope خود قابل دسترسی‌اند. `emptyStateReason` برای نبود غیبت واجد شرایط یا سرکوب گروه مشخص است. پیکربندی ناقص/غیرفعال با HTTP 409 و خطای صریح برمی‌گردد؛ مجموعه خالی به‌عنوان امتیاز صفر ناشی از خطای پیکربندی ارائه نمی‌شود. تنظیم نادرست بازه/صفحه‌بندی HTTP 400 و نبود دسترسی HTTP 403 است.

## پرسش‌های کسب‌وکاری حل‌نشده

1. آیا سازمان اصل Bradford را برای این کاربرد تصویب می‌کند؟ مالک تصویب و تاریخ اجرا چیست؟
2. کدام کلیدهای نوع مرخصی مشمول‌اند و آیا همه انواع بیماری/مراقبت/غیبت پزشکی باید حذف شوند؟
3. آیا D باید روز تقویمی باشد یا روز کاری مطابق WorkPattern و تعطیلات؟
4. آیا آخرهفته و تعطیلات داخل غیبت، spell را می‌شکنند یا در D شمرده می‌شوند؟ قرارداد فعلی آن‌ها را می‌شمارد و spell را نمی‌شکند.
5. مرخصی نیم‌روز/ساعتی چگونه به تاریخ و واحد D تبدیل شود و چند نوبت در یک روز چند spell است؟
6. آیا مرخصی `WITHDRAWAL_PENDING` تا تأیید لغو باید غیبت محسوب شود؟
7. آیا امتیاز کارکنان پاره‌وقت باید با FTE یا برنامه کاری تعدیل شود؟ قرارداد فعلی هیچ تعدیلی ندارد.
8. آیا جمعیت و داده تاریخی باید بر وضعیت استخدام حسابرسی‌شده (تعلیق/خاتمه) در هر روز نیز منطبق شود یا فقط تاریخ شروع/پایان اشتغال ملاک است؟
9. حداقل اندازه گروه برای خروجی فردی HR و سیاست دسترسی به امتیاز فردی چه باشد؟
10. آیا آستانه‌های تنظیم‌شده باید در خروجی API برچسب/اقدام ایجاد کنند؟ این نسخه از امتیاز برای تصمیم خودکار یا انضباطی استفاده نمی‌کند.

تا پاسخ و تصویب این موارد، API و مستندات آن باید provisional تلقی شوند.
