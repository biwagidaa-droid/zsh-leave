## ۳. وضعیت واقعی پیش از اجرا

### Backend و داده

- Backend یک پروژه Django/DRF است؛ منطق خالص دامنه در `backend/zsh_core` و مدل‌ها/مسیرهای محدود اجرایی در `backend/leave` قرار دارند.
- مسیرهای مستندشده و موجود API شامل سلامت، آمادگی، تبدیل تقویم و تقویم/تعطیلات/الگوی کاری/سیاست و برآورد روز کاری هستند.
- براساس قرارداد API و گزارش‌های قبلی، احراز هویت عملیاتیِ کامل، RBAC سازمانی، چرخه درخواست/تأیید، دفترکل عملیاتی سهمیه، API گزارش‌ها، Job/Notification و عملیات HR در Backend تکمیل نشده‌اند. مدل/سرویس تقویم و سیاست وجود دارد، اما برای محیط PostgreSQL آزموده نشده است.
- تنظیم Production به PostgreSQL نیاز دارد؛ تنظیم آزمون از SQLite استفاده می‌کند. فایل SQLite محلی موجود است، اما آزمون‌ها روی پایگاه داده موقت آزمون اجرا شدند.
- سه migration در کد وجود دارد؛ مهاجرت از پایگاه داده خالی و سازگاری PostgreSQL در این ممیزی اجرا نشد.

### Frontend

- برنامه React/TypeScript/Vite دارای مسیرهای کارمند، HR، مدیر و Admin و صفحه‌هایی برای درخواست، تقویم، گزارش و تنظیمات است؛ وجود صفحه به‌تنهایی اتصال عملیاتی آن را ثابت نمی‌کند.
- `frontend/src/api/index.ts` به‌طور پیش‌فرض Demo API را انتخاب می‌کند؛ فقط `VITE_DEMO_MODE=false` مسیر HTTP را فعال می‌کند. قطع API نباید با داده Demo به‌عنوان داده واقعی جبران شود.
- قرارداد Client گسترده‌تر از API واقعی Backend است. بنابراین بسیاری از مسیرهای UI و گزارش‌ها هنوز داده عملیاتی واقعی دریافت نمی‌کنند.
- پروژه تست واحد Frontend دارد؛ زیرساخت یا اجرای E2E مرورگر در شواهد بررسی‌شده یافت نشد.

## ۶. ریسک‌ها و محدودیت‌های آغاز کار

1. نبود جریان عملیاتی سرتاسری Backend برای درخواست، تأیید و دفترکل مانع گزارش‌های قابل‌اتکا و داشبوردهای مدیریتی است.
2. فعال‌بودن Demo به‌صورت پیش‌فرض امکان نمایش داده نمایشی در صورت پیکربندی نامناسب را ایجاد می‌کند.
3. مدل مجوز و scope سازمانی نهایی نشده است؛ نقش UI کنترل دسترسی سمت سرور نیست.
4. SQLite بعضی قیود PostgreSQL را اجرا نمی‌کند؛ هیچ ادعای صحت قیود/تراکنش در PostgreSQL در این گزارش وجود ندارد.
5. سیاست‌های سازمانیِ دسترسی Bradford، نگهداری داده/پیوست، RPO/RTO، اعلان‌ها و زمان‌بندی/انتقال سهمیه نیازمند تأیید سازمان هستند.
6. استقرار روی زیرساخت سازمان، اجرای Migration عملیاتی، تغییر داده واقعی، Commit، Push و Release در این کار بدون مجوز انجام نمی‌شود.

## ۷. گام بعدی

این گزارش پیش از هر تغییر کد ثبت شد. ادامه کار باید با اصلاح پیش‌نیازهای مسدودکننده و سپس اجرای فازهای ۹، ۱۰ و ۱۱ به‌ترتیب انجام شود. برای هر فاز گزارش مستقل و شواهد آزمون ثبت خواهد شد؛ قابلیت‌های فاقد شواهد با وضعیت `PARTIAL`، `BLOCKED` یا `NOT VERIFIED` گزارش می‌شوند، نه `COMPLETE`.
